---
name: propops-documentation-adr
description: Use when a code change affects architecture, domain concepts, data ownership, integration boundaries, security model, operational workflow, or when the user asks to document a technical decision.
---

1. Update existing docs rather than creating duplicate sources of truth.
2. Create an ADR for a durable architectural decision with meaningful alternatives/tradeoffs.
3. ADRs must include status, date, context, decision, and consequences.
4. Keep docs implementation-aware but not tied to accidental file paths unless necessary.
5. When renaming a domain concept, update README, domain model, relevant skills, and code terminology together.
6. Record assumptions and explicit non-goals.
7. Do not document aspirational behavior as already implemented; label roadmap/future work clearly.
